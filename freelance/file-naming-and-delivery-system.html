Final_FINAL_v3: A File Naming and Delivery System for Designers

This article contains affiliate links. If you sign up through one, we may earn a commission at no extra cost to you. Full disclosure.

Every designer has a folder that looks like this: logo_final.psd, logo_final2.psd, logo_FINAL_v3_reallyfinal.psd. The problem is not tidiness. The problem starts when a client asks you to go back to the version they approved two weeks ago, and you cannot tell which file that was — or when you send a delivery package and realise the print file, the web exports, and the source files do not match.

Version chaos costs time in two places. First, you lose minutes hunting for the right file on every revision. Second, you risk delivering the wrong version, which creates rework and an awkward conversation. A fixed naming formula and a fixed folder structure remove both risks. This guide gives you a system you can copy today: a naming formula, a folder template, version rules, a delivery checklist, and a delivery email you can reuse.

Why versions get out of control

Most naming problems come from three habits. The first is naming files by feeling instead of by rule — "new," "updated," and "final" mean something different every day. The second is saving revisions as separate files without a status marker, so work-in-progress and approved work sit side by side with nothing to tell them apart. The third is receiving client feedback in scattered places, so a file gets revised before an earlier comment is resolved. If that last one sounds familiar, see our guide on how to collect design feedback in one place.

Large files make it worse. A layered source file, a set of print exports, and a folder of linked images can be too big for a quick email attachment, so files end up split across email, chat, and whatever transfer tool was open that day. Six months later, nobody — including you — knows where the master copy lives. The fix is boring but effective: one formula for names, one structure for folders, and one place where approved files are stored.

The file naming formula

Use this pattern for every client file:

Client_Project_Deliverable_v##_STATUS.extension

For example: AcmeCo_BrandRefresh_LogoPrimary_v03_APPROVED.ai

Each part does a specific job:

  • Client — the client or brand name, shortened but consistent. Pick one spelling and never vary it.
  • Project — the project name, so files from different jobs for the same client never mix.
  • Deliverable — what the file actually is: LogoPrimary, HomepageHero, MenuA4, and so on.
  • v## — a two-digit version number. Always two digits (v01, v02, v10) so files sort correctly in a list.
  • STATUS — one of three values only: WIP (work in progress), APPROVED (the client has signed this version off), or FINAL (the delivery version, used only in the delivery package).

Use underscores between parts and avoid spaces, which can break links and scripts. Keep the deliverable names short and predictable across projects, so the same kind of file always gets the same name.

A folder structure that stays clean

Create the same five folders at the start of every project. The numbers keep them in workflow order in any file browser:

ClientName_ProjectName/
  01_Brief/
    - brief, contract, intake answers, brand guidelines received
  02_Working/
    - source files in progress (all _WIP versions live here)
  03_Review/
    - exports sent to the client for feedback (PDFs, JPGs, proofs)
  04_Approved/
    - the exact files the client approved (copies, never edited)
  05_Delivery/
    - the final delivery package only (all _FINAL files)

The rule that makes this work: files only move forward. A working file stays in 02_Working while it changes. When you send a proof, export it into 03_Review. When the client approves a version, copy it into 04_Approved and add APPROVED to its name. Build the delivery package in 05_Delivery from the approved copies — never from a working file you edited afterwards.

Version rules that prevent the "wrong file" email

  1. One file, one version number. Every meaningful save that leaves your desk gets a new number. If a file was sent to the client, it is never overwritten.
  2. Approval is a copy, not a rename. When a client approves v03, copy that exact file into 04_Approved with the APPROVED status. Keep working copies separate, so the approved version can always be restored exactly as it was.
  3. FINAL is reserved for delivery. Nothing is called FINAL until it is in the delivery package in 05_Delivery. This single rule ends the final_v3 problem, because "final" stops being an opinion and becomes a location.
  4. Never edit an approved or final file. If something changes after approval, it becomes a new version (v04, WIP) and goes through review and approval again.
  5. Date your exports, not your sources. Source files carry version numbers. If you also want dates on review exports, add them at the end of the export name only, so source sorting stays clean.

The final delivery checklist

Run through this list before anything leaves 05_Delivery:

  • Formats: Source files (for example AI, PSD, INDD, or Figma export) plus ready-to-use exports — PDF for print and documents, PNG/JPG for raster use, SVG/EPS for logos and vector assets — as agreed in the project scope.
  • Colour mode: Print files in CMYK; screen files in RGB. Check every export, not just the first one, and confirm the PDF uses the colour profile your printer or client requested.
  • Fonts: For print files, convert text to outlines where the printer requires it, and keep a separate editable copy with live text. Only include font files if the font licence allows it — if it does not, tell the client which fonts to license and note this in the delivery email.
  • Images: Embed linked images in print files, or package them with the source files so nothing arrives as a missing-link error. Check effective resolution on placed images for print work.
  • Print setup: Bleed added on all trimmed edges, crop marks (trim marks) included if the printer wants them, and page size matching the finished trim size.
  • Names and versions: Every delivered file follows the naming formula, carries the FINAL status, and matches the approved version in 04_Approved.
  • Contents check: Open the delivery folder fresh and open each file once. If you cannot open it, neither can the client.

Delivery email template

Send one email with the delivery. It confirms what was delivered, where it lives, and what happens next:

Subject: Final delivery — [Project Name] ([Client Name])

Hi [Name],

Your final files for [Project Name] are ready. You can download the
complete delivery package here: [link]

What's included:
- Source files: [e.g. AI and INDD files for the logo and menu]
- Print files: [e.g. CMYK PDFs with bleed and crop marks]
- Web/screen files: [e.g. PNG, JPG, and SVG exports in RGB]

These files match the versions you approved on [date]. The approved
versions are also kept on my side, so if you need a file re-sent or a
small export in a different size, just ask.

One note on fonts: [the files use X / font files are not included
because of licensing — the fonts can be licensed from Y].

If anything won't open or looks off, reply to this email within
[number] days and I'll fix it. After that, changes are treated as a
new revision.

Thanks again for the project,
[Your name]
[Business name / contact details]

Where the files live: cloud storage for large design files

The system above only works if approved and final files live in one reliable place that both you and the client can reach. When choosing cloud storage for design work, check four things: whether there is a file size limit (large layered files and video exports can be several gigabytes), whether old versions can be restored after an accidental overwrite, whether shared links can be protected with a password and an expiry date, and how much storage you get for the price.

On its official pages, pCloud states there is no file size limit, which matters when a single delivery package runs to gigabytes. Paid plans come in 500 GB, 2 TB, and 10 TB sizes, and each can be paid monthly, annually, or as a one-time lifetime purchase.

The weaknesses are worth knowing before you commit. Zero-knowledge encryption (pCloud Encryption) is a paid add-on, not included as standard. pCloud is storage and sharing, not a collaborative document editing suite, so it will not replace the tool where you and a client edit copy together. The lifetime option only pays off over time — on an annual-price comparison it takes roughly five years to break even, so it is poor value if you switch services sooner. And shared links have a monthly traffic limit that varies by plan, which can matter if many people download large delivery files.

FAQ

Should I include the date in file names as well as a version number?
For source files, a version number is usually enough, and it sorts more reliably. Dates help most on review exports and delivery packages, where "when was this sent?" is the question. If you use both, keep the order consistent: version first, date last.

What if a client keeps renaming files on their side?
Expect it, and design around it. Your 04_Approved folder is the record of what was approved, under your naming system. In the delivery email, refer to files by their delivered names so there is a written record the client can search later.

How long should I keep old versions and approved files?
Keep approved versions and final delivery packages for as long as your contract or local rules require, and at least as long as the client might reasonably ask for a re-send. Work-in-progress versions can be pruned once a project closes, but the approved copy is the one file you never delete casually — restoring it is the whole point of the system.
